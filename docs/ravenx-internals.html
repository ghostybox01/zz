RavenX 2.0 — Internals Reference

Complete engineering reference for the scanner pipeline, all detectors, validators, and supply-chain modules. Use this document to understand, audit, and improve scanner logic.

System Overview

RavenX is a Go binary that discovers exposed credentials and security misconfigurations across web surfaces. It is not a passive SAST tool — it makes live HTTP requests against real targets and validates every candidate credential against the issuing API.

Concurrency Model

RavenX is highly concurrent. Each target gets a goroutine pool. Within a target, path probing runs per-path goroutines capped by a sync.WaitGroup. Validators run in goroutines spawned with go a.Check*(). Gap-closer detectors run go a.scanWebhookURLs(), go a.checkFirebaseOpenRules(), etc. — all async, non-blocking.

Rate limiting uses do429Retry() — exponential backoff on 429 responses, up to configurable max attempts. The 429 sleep duration is read from the Retry-After header when present.

Detection Pipeline

Every fetched HTTP response body passes through the same pipeline. Understanding this flow is essential for adding new detectors.

checkAndSaveKeys (main.go:3903)

The central dispatcher. Every scan path ends here. Execution order:

// 1. Honeypot / bait detection — bail immediately if triggered
if a.HoneypotPattern.MatchString(text) { return }

// 2. DS_Store short-circuit — binary content, send to dedicated parser
if strings.Contains(sourceURL, "DS_Store") {
    a.extractDSStoreFilenames(text, sourceURL); return
}

// 3. Terraform state short-circuit — check signature before regex
if strings.Contains(sourceURL, "(tfstate:") {
    return // recursion guard
}

// 4. Base64 decode attempt — catches obfuscated keys in JS
tryDecodeBase64(text)

// 5. Core regex battery — 200+ patterns across all credential types
// Each match dispatches to its specific Check*() validator

// 6. SMTP credential extraction
a.extractAndTestSMTP(text, sourceURL)

// 7. Gap-closer detectors (all async)
go a.scanEntropyPass(contentToScan, sourceURL)
go a.scanWebhookURLs(contentToScan, sourceURL)
go a.checkFirebaseOpenRules(contentToScan, sourceURL)
go a.parseTerraformStateContent(contentToScan, sourceURL)
AST content path: When the JS scanner finds a source map URL (//# sourceMappingURL=), it fetches the .map file and passes its sources[*] content back through checkAndSaveKeys with a (from AST: url) suffix in the sourceURL. This prevents infinite recursion.

Prefilter & Target Queue

Before any deep scanning, each target passes through a prefilter that checks liveness and classifies the surface:

IP / Domain list
→
HEAD + GET / (timeout 8s)
→
Status 200/30x?
→
Fingerprint (Server, X-Powered-By)
→
Blacklist check
→
prefilter_hits.txt → scan queue

Targets that return honeypot bait patterns (configurable regex) are permanently skipped and logged to honeypot_detected.txt.

The deduplication file dedup.txt is loaded at startup — any target already in it is skipped. After a successful scan, the target is appended. This makes resumable scans safe across binary restarts.

Crawler — Enhancer (main.go:783)

The Enhancer struct performs breadth-first crawling from the root URL up to a configurable depth. It extracts:

  • All <a href> links within the same origin
  • All <script src> references (feeds the JS scanner)
  • Sitemap URLs from /sitemap.xml and /robots.txt
  • Response headers (Server, X-Powered-By, CF-Ray, Strict-Transport-Security, Set-Cookie)

Headers are scanned by scanHeaders() which checks Set-Cookie for session tokens and API keys embedded in cookie values.

Path Scan Loop (main.go:5460)

After crawling, a consolidated commonPaths slice is assembled from all enabled scanners. Each path is probed concurrently (goroutine-per-path, sync.WaitGroup controlled). On a 200/206 response the body is dispatched:

if strings.Contains(pth, ".git/config") {
    a.extractGitCredentials(string(b), fullURL)    // git-specific parser
} else {
    a.checkAndSaveKeys(string(b), fullURL)          // main credential detector
}

// Post-body hooks — fire regardless of which branch above ran
if GPLScan && isGraphQL(pth) { go a.probeGraphQLIntrospection(fullURL) }
if LibScan && isPackageManifest(pth) {
    go a.checkPackageManifestCVEs(content, fullURL, pth)
    go a.checkNPMSupplyChain(content, fullURL, pth)
}

LIVE

GPL (GraphQL) Scanner gpl_scan

On any path containing graphql, /gql, or literally /query, POSTs a standard introspection query ({ __schema { types { name } } }). A successful response is saved to graphql_found.txt along with the full type list — which often reveals internal resolver names and business logic fields.

Output: graphql_found.txt
LIVE

Git Config Scanner git_config_scan

Fetches /.git/config and /.gitconfig. The dedicated extractGitCredentials() parser (rather than checkAndSaveKeys) extracts remote URLs in the form https://token@github.com/org/repo, strips and validates the token.

ScanRepo uses git clone --no-single-branch --depth 50 so the last 50 commits across all branches are checked — catching keys that were committed then reverted.

Output: git_credentials_found.txt
LIVE

Docker Compose Scanner docker_scan

Probes /docker-compose.yml, /docker-compose.yaml, /docker-compose.prod.yml, and /.docker/docker-compose.yml. The YAML is passed through checkAndSaveKeys which extracts environment: block values via the same credential regex battery.

LIVE

PHP / phpinfo Scanner phpinfo_scan

Probes 8 common phpinfo paths. The HTML table parser extractValueFromPhpInfoTable() specifically extracts mysql.default_password, mysqli.default_pw, and any environment variable rows — phpinfo leaks the full $_SERVER superglobal including credentials passed as env vars to the PHP process.

LIVE

SSH Key Scanner ssh_scan

Probes paths like /.ssh/id_rsa, /.ssh/id_ed25519, /.ssh/id_ecdsa. Detects the PEM preamble -----BEGIN * PRIVATE KEY-----. Optionally extracts the key fingerprint for identification without storing the key material in plaintext output.

Output: ssh_keys_found.txt

Gap-Closer Detectors

These run after the main regex battery, all asynchronously. They catch credential classes that don't match any fixed pattern.

DETECTOR

Shannon Entropy Detection

Scans for key|token|secret|auth|api|credential = "HIGH_ENTROPY_STRING" patterns. Any value ≥ 4.5 bits/character (calculated via Shannon's formula over the character frequency distribution) that isn't already matched by a named regex is saved as a high-entropy finding.

The threshold of 4.5 bits/char catches Base64-encoded 128-bit+ keys while excluding natural-language values and UUIDs. Pure random hex (5.0 bits/char) and Base64 (5.95 bits/char theoretical) both pass the gate comfortably.

Output: entropy_found.txt Gate: not called recursively (sourceURL check)
DETECTOR

Webhook URL Extraction + Validation

Three regexes match inline webhook URLs:

  • Slack: hooks.slack.com/services/T.../B.../... — validated by POSTing {"text":"."} and checking for response "ok"
  • Discord: discord.com/api/webhooks/ID/TOKEN — validated by GET 200 response
  • PagerDuty: events.pagerduty.com/integration/.../enqueue — saved, not live-tested (would page someone)
Output: slack_webhook_found.txt valid_slack_webhook.txt discord_webhook_found.txt pagerduty_webhook_found.txt
DETECTOR

Firebase Open Rules Testing

Detects Firebase config blocks in JS source (pattern: projectId: "..."). For each discovered project ID, two goroutines probe unauthenticated access:

  1. Firestore REST: GET firestore.googleapis.com/v1/projects/{id}/databases/(default)/documents without auth header — open if 200
  2. Realtime DB: GET {id}.firebaseio.com/.json and {id}-default-rtdb.firebaseio.com/.json — open if non-401
Output: firebase_open_found.txt
DETECTOR

Terraform State JSON Walker

Triggered when fetchedContent contains both "terraform_version" and "resources" strings (fast pre-check before full parse). Regex-walks the JSON extracting values from any attribute key matching: access_key, secret_key, password, private_key_pem, service_account_key, auth_token, client_secret, sas_token.

Each extracted value is re-dispatched to checkAndSaveKeys with a (tfstate:attrKey) suffix in the URL — this triggers the full validator battery on each found value, and the suffix prevents infinite recursion back into the Terraform parser.

Output: terraform_state_found.txt
DETECTOR

.DS_Store Binary Parser

checkAndSaveKeys early-returns for .DS_Store URLs, handing off to extractDSStoreFilenames() which scans the binary for printable ASCII strings of length 4–255 characters (the format stores filename strings as Pascal-length-prefixed records). Result: a full server directory listing extracted from a single 10–30 KB binary file — invaluable for discovering hidden paths to probe.

Output: ds_store_found.txt ds_store_paths.txt
FPP

False-Positive Prevention (isFalsePositiveCred)

Before any credential candidate is sent to a validator, isFalsePositiveCred() gates it. Current filter rules:

  • Substring match against 30+ placeholder terms: example, changeme, placeholder, your_, ${, %(, todo, replace_me, etc.
  • All-same-character strings (e.g. AAAAAAAAAAAAAAAA)
  • Pure numeric strings ≥ 8 digits
  • UUID-format strings (/^[0-9a-f]{8}-…/) — valid format but not API keys
  • Known example domain fragments: example.com, test.com, localhost

Additionally, isTestFilePath(sourceURL) detects test/spec/fixture file paths — findings from these sources should be treated with lower confidence.

Validators

Every candidate key passes through KnownKeys.LoadOrStore first — duplicates are discarded before any network call is made. Validators are live API calls with timeouts and 429-retry logic.

AWS

AWS Validator — Deep Scan

Stage 1 — Identity: sts:GetCallerIdentity — confirms key is valid, extracts ARN, account ID, user/role name.

Stage 2 — IAM Audit: iam:GetUser + iam:ListAttachedUserPolicies + iam:ListUserPolicies — builds a policy summary showing what the key can actually do.

Stage 3 — Parallel service probes (all async):

  • SES: ses:GetSendQuota across all regions — identifies sending limits (high quota = high spam value)
  • SNS: sns:GetSMSSandboxAccountStatus + spending limits
  • S3: s3:ListBuckets — full bucket list with public-access flags
  • SSM: ssm:DescribeParameters — lists Parameter Store entries (often contain secrets)
  • Fargate: ecs:DescribeClusters across regions — detects running workloads
  • Federation URL: signs a temporary console URL valid for 12 hours — direct web console access

Stage 4 — IAM Role Escalation: iam:ListRoles (max 100) then sts:AssumeRole per role — finds privilege escalation paths where a limited key can assume an admin role.

Output: aws_valid.txt aws_deep_scan.txt aws_ssm.txt aws_iam_escalation.txt

GITHUB

GitHub Token Validator

Calls GET /user with the token. On success:

  1. Extracts X-OAuth-Scopes header — the full list of granted permissions (e.g. repo, admin:org, workflow)
  2. Risk-tiers the scopes: any of admin:org, delete_repo, workflow, admin:repo_hook → 🔴 HIGH-VALUE
  3. If github_token_deep_scan enabled: enumerates all repos the token can see, then calls ScanRepo() on each — git clone at depth 50 across all branches
Output: valid_github.txt
CRYPTO

Crypto Wallet Validator

Detects Ethereum private keys (64-char hex, often preceded by 0x). For each candidate:

  1. Derives the public address using ethAddressFromPrivKey() (secp256k1 ECDSA, Keccak-256 hash)
  2. Queries ethWalletStatus(address) against a public Ethereum RPC endpoint — returns ETH balance and nonce
  3. Non-zero balance wallets generate a Telegram CRITICAL alert
Findings are displayed only. No transactions are ever initiated. The private key material is only used for address derivation.
Output: valid_crypto.txt

Supply Chain Modules

NEW

OSV CVE Integration — detectors_osv_cve.go

Runs when a package manifest is fetched and lib_scan is enabled. Parses exact package versions and queries api.osv.dev/v1/querybatch (free, no auth, up to 200 packages per batch).

Supported ecosystems: npm (package.json, yarn.lock, package-lock.json), PyPI (requirements.txt, Pipfile.lock, pyproject.toml), Go (go.mod), Packagist (composer.json), RubyGems (Gemfile.lock)

Severity classification from CVSS vector: counts :H (High) and :C (Complete) impact markers. Network-reachable (AV:N) + all-high impacts → CRITICAL. Three high markers → HIGH. Others → MEDIUM/LOW.

Telegram alerts fire for CRITICAL and HIGH findings only (capped at 10 lines per message to stay within Telegram's 4096-char limit).

Output: cve_found.txt
NEW

npm Supply Chain — detectors_npm_supply_chain.go

Three checks on every fetched package.json:

1. Typosquat Detection — Levenshtein edit distance ≤ 1 (or ≤ 2 for short names ≤ 8 chars) against a curated list of 80 commonly impersonated npm packages. Runs locally with no API calls — result is immediate.

2. npm Registry Metadata (async, fires only for typosquat hits) — queries registry.npmjs.org/{package} for: package age (flag if < 30 days old), maintainer count (flag if zero), missing repository URL.

3. R2S Passive — for packages that declare a repository URL, sends a HEAD request to verify the source code repository is reachable. A 404/410 response means the declared source no longer exists — the package may have been taken over or the repo deleted post-publish.

Output: npm_supply_chain.txt

Telegram Alert System

All high-value findings trigger an async Telegram message via Bot API. Key design decisions:

Deduplication

Each outbound message is SHA-256 hashed. A local sync.Map (telegramSent) prevents the same message from being sent twice within a session. Duplicate messages are logged with pterm.Debug as [TELEGRAM SKIP].

Alert Tiers

CRITICAL: AWS valid, crypto wallet balance, eval/exec SAST, IAM escalation, new CVE CRITICAL.
HIGH: Email API valid, GitHub HIGH-VALUE scope, typosquat hit, new package (<30d), R2S 404.
MEDIUM: SMTP valid, open Firebase, Terraform state, webhook validated.

Improving Alert Logic

Current gap: All valid finds generate a Telegram message regardless of scan volume. At scale (1000+ targets/hour), this floods the channel. A recommended improvement is a batching layer: accumulate findings per-scan-session, flush a summary every N findings or every T seconds.
Dedup note: The in-session hash dedup prevents repeat alerts for the same key across different pages of the same target, but does NOT persist across binary restarts. If the scanner restarts mid-run, the same key found again will re-alert.

Logic Improvement Opportunities

Areas identified for the next iteration:

Detection Quality

1. Confidence Scoring

Currently all credential candidates are treated equally. Adding a confidence tier (1–5) based on: source file type (config > JS bundle > minified), match pattern specificity (exact prefix match > generic regex), proximity to other credentials (co-location boosts confidence) would let the UI surface the highest-confidence finds first.

2. Context Window for FPP

The current FPP checks the credential value in isolation. Adding a ±3-line context check — if the surrounding lines contain test, mock, fake, example — would catch test credentials embedded in real files without being in a test-path URL.

3. Full AST JS SAST (Phase 2)

The current JS SAST module uses high-signal regexes. A real AST-based approach would require either (a) bundling a Semgrep binary with the scanner and running it as a subprocess, or (b) using a Go-native JS parser (e.g. github.com/nicholasgasior/gsfmt or calling Node as a subprocess). This would enable taint tracking from user-controlled sources to dangerous sinks.

4. OSV Cache Persistence

Currently the OSV CVE check has no cross-session cache. A simple local SQLite or JSON file mapping ecosystem:pkg@ver → []CVE-IDs would avoid re-querying the same package across different targets in a long scan run.

5. npm Supply Chain — Download Count Heuristic

The registry API returns download statistics at api.npmjs.org/downloads/point/last-month/{package}. A package with < 100 downloads/month that isn't a private internal package is significantly more suspicious than one with 10M+.
